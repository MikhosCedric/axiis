## What Axiis is

## Conventions that matter
- **Command pattern.** Logic lives in `commands.ts` taking an `ItemsRepo`, tested against `fakeRepo` in `src/features/today/test-support.ts`. Server actions in `actions.ts` are thin: zod-validate, call the command, `refresh()`.
- **Pure logic has no React.** Score layout, snapping, drop-to-patch are plain modules with tests.
- **Boundaries parse, internals trust.** Rows and env are parsed with zod once. `Schedule` is a union (`unscheduled | day | timed`), never nullable columns past the mapper.
- **Time.** Schedules are built from local wall-clock minutes with `instantAt`, never `+24h` arithmetic.
- **State is shown by line form** (solid live, dashed planned, hollow done). Accent colour means now, drag target or primary focus only. Voice: quiet, plain, no exclamation marks, no guilt copy.
- **Next.js 16.** Breaking changes from older versions. Read `node_modules/next/dist/docs/` before touching routing, proxy (formerly middleware), fonts or server actions. `next dev` appends an agent-rules block to `CLAUDE.md`; do not commit that.
- **Windows.** Files use CRLF in the working copy. Prefer the Edit tool over regex scripts on source files.

## Commands

npm run dev          # needs .env.local (Supabase URL + publishable key)
npm run lint && npm run typecheck && npm test && npm run build   # what CI runs

## Known gaps and risks
- The e2e suite now visits the real signed-in routes through a fake session compiled only into the browser-test build with in-memory repos (`docs/e2e-session.md`): the proxy, layouts, nav rail and server actions are covered there. Supabase Auth (magic link, Google, callback, refresh), row-level security and the Supabase repos are not, because the fake session replaces them.
- Saves through the real repo and row-level security have been verified by unit tests and a rolled-back SQL check, but not through a signed-in browser session against Supabase (the agent cannot receive the magic link).
- The Score/List view-transition morph has not been seen playing; the preview pane reports the page hidden.
- Touch drag tested with synthetic events only.
- Restoring a skipped day is verified by unit tests against `fakeRepo` and the detail harness (e2e and axe), not by a signed-in session. "Skipped dates" lists every skipped date of a series, with no cap.
- Series time, "Any time" and first day are verified by unit tests against `fakeRepo` (including DST days) and the score and detail harnesses (e2e and axe), not by a signed-in session. The Time row is two text fields on the reader's Time format that read either clock; date fields (First day, the repeat end, the day and week pickers) are still native and show dates in the browser's locale format.
- The detail panel goes inert and `aria-busy` while the day, week or inbox screen switches items. A link inside the panel (the "Part of" parent link) navigates without that pending state.
- Tags are verified by unit tests against `fakeRepo`, a stubbed PostgREST test, a PGlite export test and the tags and settings harnesses (e2e and axe), not by a signed-in session. A `#tag` search with words filters the 30 text hits search returns, so a common word can hide older tagged matches. A tag-only search lists stored items, so an override of a tagged series shows only under its series.
- Planning, Type and Due from the detail panel are verified by unit tests against `fakeRepo` (DST days included) and the detail harness (e2e and axe at desktop, dark and 375px), not by a signed-in session. Due is still shown only in the panel and the export; nothing sorts or warns by it. An event with no time is allowed and drawn as an any-time item.
- The Inbox is verified by unit tests, a stubbed PostgREST query test and its dev harness (e2e and axe), not by a signed-in session.
- Lists are verified by unit tests against `fakeRepo`, a stubbed PostgREST query test and the `/dev/lists` harness (e2e and axe, with an item open), not by a signed-in session. A series cannot have subtasks, so a repeating checklist's row shows how it repeats instead of progress. Progress counts every live line, so a dropped line counts as not done, as the Inbox and Score counts already do.
- The tags and lists harnesses keep their store in memory, so a page reload empties it. The browser tests run a production build, which never reloads a page on its own.
- Capture words and palette actions are verified by unit tests against `fakeRepo` and the score, week, inbox, lists and palette harnesses (e2e and axe), not by a signed-in session. The parser knows English words only, and a day after a preposition such as "for" stays in the title, so "Groceries for Sunday" is not planned.
- Notes, week, settings, export and deletion are verified by unit tests, rolled-back SQL on the hosted project and dev harnesses, not by a signed-in browser session.
- A series whose first date is a day the clocks change, timed before `fix-known-gaps`, was stored with its length in real minutes, so its wall-clock end on that day is an hour off what was typed, and every occurrence now repeats that end. Setting its time again fixes it. No query found how many hosted rows this touches.
- The purge and the tag counts are tested in PGlite and with a stubbed PostgREST, not against the hosted project or a signed-in session.
- `[`/`]` shortcuts do nothing on layouts where those keys need AltGr; the on-screen buttons work everywhere.
- Rate limits (audit of 2026-10-14). Every server action and route handler runs as the signed-in user, and the same session can call PostgREST directly, so a throttle in an action would be bypassed. What bounds each:
  - Row-adding writes (capture, Lists capture, subtasks, new and linked notes, links, tags, areas, and any change to one day of a series, which stores an override): `0006` caps rows held (applied), `0007` caps rows added a minute (applied).
  - Update-only writes (rename, move, place, plan, time, due, type, done, note saves, area and tag renames) and deletes: no database rate limit. They do not grow an account; the Vercel rule on the `next-action` header is their bound. A loop of note saves rewrites up to 512 KB a call.
  - Reads (pages, search at 30 hits, palette, the export route): bounded by the quotas and PostgREST max rows; not rate-limited. A guard on the export would not help, since the same session can page the same rows from PostgREST; the Vercel rule on `/settings/export` bounds the function cost.
  - Sign-in: the email is validated, one browser waits 30 seconds between links (unsigned cookie, `src/app/(auth)/login/cooldown.ts`), Supabase refuses a second email to one address within its minimum interval, and the project's emails-per-hour limit caps the sender. Google only builds a redirect. `/auth/callback` needs the PKCE verifier cookie. None of this limits per IP; that waits on the Vercel firewall rules in `docs/launch-checklist.md`, Rate limits.
  - Supabase Auth is called from Vercel functions, so its per-IP limits probably count all users against Vercel's addresses (inferred, not measured). The checklist raises them and says what to watch in the Auth logs.
  - `delete_my_account` is one call per account; account deletion is not throttled and needs none.
